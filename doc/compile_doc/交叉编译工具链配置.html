OSZ 交叉编译工具链配置说明

从“改脚本适配一台机器”到“设两个环境变量适配任意工具链”，CMake 与 Make 两条构建路径共用同一套查找规则

文档版本v1.1（CMake 与 Make 两条路径均已自适应）
更新日期2026-11-24
代码基线main（2026-11-24，含 Make 路径自适应）
适用对象在非 Linux 主机 / 非官方工具链上构建 rv32 目标的人

01结论先行

旧脚本把三件事写死在仓库里：工具链前缀（riscv32-unknown-elf）、工具链目录（tools/toolchain 符号链接指向某个绝对路径）、gcc 版本目录（lib/gcc/.../14.2.0）。任何一条不匹配，配置阶段就失败，而这些都在受版本控制的文件里，换机器就必须改代码。

现在的做法是：仓库只负责“按约定找工具链”，具体路径由使用者用两个变量提供，其余信息（sysroot、libgcc 位置、是否带 C++ 前端）由编译器自己回答。

2 个变量OSZ_CROSS_ROOT / OSZ_CROSS_PREFIX
4 级来源显式变量 → tools/toolchain → 旧 ~/tools/toolchains → PATH
0 处硬编码目录结构、gcc 版本、C++ 前端都不再假设
同一产物rv32 ELF，链接脚本与会话常量保持不变

02当前交叉编译架构

本机实际跑通的链路如下：主机是 macOS（arm64），工具链是 xPack 的 riscv-none-elf-gcc 15.2.0，目标 rv32g / ilp32d，产物是 32 位 RISC-V 静态 ELF。

环节本项目取值是否可配置
主机macOS（arm64）；Linux 同样适用—
工具链前缀本机实测 riscv-none-elf（xPack GCC 15.2.0）OSZ_CROSS_PREFIX
工具链根目录本机 /Users/zyzs/tools/riscv/xpack-riscv-none-elf-gcc-15.2.0-1OSZ_CROSS_ROOT
目标架构 / ABIrv32g / ilp32dOSZ_CROSS_ARCH / OSZ_CROSS_ABI
编译特征-ffreestanding -nostdlib -g工具链文件内固定
链接特征-nostdlib -nostartfiles -Wl,--gc-sections -T osz.ld工具链文件内固定
产物build/targets/qemu_virt/target_qemu（ELF32，静态）—
验证命令file / readelf -h / nm（工具链自带 binutils）—
跑起来的两条通道（都不依赖本机 QEMU）：①本机仿真平台 localhost:8080 工作台用的那份 wasm 内核（front/assets/pkg/riscv_sim_kernel.js），可用 node tools/sim/run_on_platform.mjs output/image/osz.elf 直接驱动，console 字节走 stdout、统计走 stderr；②Spike 参考侧 spike --isa=rv32imc_zicsr_zicclsm_zifencei_zicntr -m… output/image/osz.elf。两侧 console 可以逐字节 cmp。
⚠️ 平台侧自 v0.76 起「无板不装载」：必须先取模板（qemu-virt）再 SetMemoryMap，否则内核以 E_PLT-22 拒绝 —— 脚本已按这个顺序走。
为什么强调“编译器自己回答”：sysroot 与 libgcc 的实际位置由发行包的布局决定，官方 riscv-gnu-toolchain 是 <prefix>/riscv32-unknown-elf/lib，xPack 是 <prefix>/riscv-none-elf/lib，版本号还会随升级变化。用 --print-sysroot 与 -print-file-name=libgcc.a 问编译器，就不会再出现“升一版 gcc 就要改脚本”的情况。

03工具链查找与选择机制

construct/cmake/riscv32_toolchain.cmake 在 project() 之前生效，负责把编译器与一套 binutils 注册给 CMake。Makefile 路径由 construct/script/env.sh 实现同一套顺序，两条路径解析同一台机器时得到同一个前缀，不会各说各话。

顺序来源说明
1-DOSZ_CROSS_ROOT / -DOSZ_CROSS_PREFIX优先级最高，适合脚本、CI、多工具链并存
2环境变量 OSZ_CROSS_*只在未用 -D 指定时生效，适合“这台机器的默认”
3tools/toolchain支持 <root>/bin 与 <root>/<prefix>/bin 两种布局；目录或符号链接均可，已 git-ignore
4系统 PATH最后的兜底，适合把工具链 bin 直接加进 PATH 的人
实现细节（容易被忽视的两点）：①工具链文件在 project() 之前执行，此时 CMAKE_SOURCE_DIR 还没有值，仓库根目录必须由 CMAKE_CURRENT_LIST_DIR 反推，否则 tools/toolchain 这一级永远命中不了；②find_program 会把结果写进 cache，且变量一旦有定义就跳过搜索，所以每个前缀候选都要先 unset（普通变量与 cache 两处），否则重复配置时会沿用上一轮结果，出现“前缀标签是 A、实际编译器是 B”的错配。配置末尾新增了文件名一致性自检，专门拦这种情况。

前缀同样是“给定优先、否则按发行包命名依次尝试”：用户指定的值 → riscv32-unknown-elf（官方 riscv-gnu-toolchain）→ riscv-none-elf（xPack）→ riscv64-unknown-elf（用 -march=rv32* 也能出 rv32 目标）。命中即停止。

04配置参数

变量类型默认作用
OSZ_CROSS_ROOT路径空工具链根目录（其下有 bin/）。空则查 tools/toolchain 与 PATH
OSZ_CROSS_PREFIX字符串空如 riscv-none-elf；空则自动探测
OSZ_CROSS_ARCH字符串rv32g传给 -march
OSZ_CROSS_ABI字符串ilp32d传给 -mabi
OSZ_REQUIRE_CXX布尔OFFTRUE 时工具链必须带 cc1plus，否则配置阶段直接失败
# 方式一：环境变量（换机器只改这两行）
export OSZ_CROSS_ROOT=/opt/xpack-riscv-none-elf-gcc-15.2.0-1
export OSZ_CROSS_PREFIX=riscv-none-elf
./construct/build_cmake.sh target_qemu

# 方式二：一次性命令行参数
cmake -S . -B build -DOSZ_CROSS_ROOT=$HOME/tools/xpack-gcc -DOSZ_CROSS_PREFIX=riscv-none-elf
cmake --build build -j

# 方式三：什么都不设，把工具链放进仓库 tools/toolchain（该目录已被 git-ignore）
ln -s $HOME/tools/xpack-gcc tools/toolchain
./construct/build_cmake.sh target_qemu

05C++ 前端缺失时的处理

很多 RISC-V 发行包只装 C 前端，不带 cc1plus，而旧脚本用 project(OSZ LANGUAGES C CXX ASM) 强制探测 C++ 编译器，结果“工具链能用但配置过不去”。

现在的规则：

  1. project() 只声明 C ASM；
  2. 工具链文件执行 <prefix>-g++ -print-prog-name=cc1plus，能解析成存在的绝对路径才置 OSZ_CROSS_HAS_CXX=TRUE；
  3. 为真才 enable_language(CXX)，否则跳过。内核没有 C++ 翻译单元，构建结果不变；
  4. CI 或需要完整工具链的人加 -DOSZ_REQUIRE_CXX=TRUE，缺前端时在配置阶段就看到明确错误，而不是编译到一半才失败。
不要把“跳过 CXX”理解成可以随便编译 C++：若将来真的引入 .cpp 翻译单元，缺 C++ 前端的工具链会在编译该文件时报错。OSZ_REQUIRE_CXX 就是给这种场景预留的显式闸门。

06目录与版本控制约定

路径是否纳入 git说明
construct/cmake/riscv32_toolchain.cmake是只包含查找逻辑与编译/链接参数，不含任何绝对路径
tools/toolchain否（已加入 .gitignore）本机的工具链目录或符号链接，属于环境而非代码
build/ 及各 build-* 目录否构建产物，含 targets/qemu_virt/target_qemu

07Makefile 路径（已同步改为自适应）

construct/build_make.sh 只做两件事：source construct/script/env.sh 拿到环境，然后对每个目标名跑一次 make。所以适配能力全部落在 env.sh，与 CMake 侧同一套顺序：

  1. 显式指定 OSZ_CROSS_ROOT / OSZ_CROSS_PREFIX（支持 <root>/bin 与 <root>/<prefix>/bin 两种布局）；
  2. 仓库 tools/toolchain（目录或符号链接，已 git-ignore）；
  3. 旧路径 ~/tools/toolchains：已解压的 <prefix>/bin 可直接用；只有 <prefix>.tar.gz 时自动解压到该目录再重试；
  4. PATH 中的 <prefix>-gcc。

前缀候选同样是“给定优先 → riscv32-unknown-elf → riscv-none-elf → riscv64-unknown-elf”。解析结果通过三个变量往下传，Makefile 里不再有任何写死的前缀或版本号：

变量来源 / 默认在 Makefile 里的落点
CROSS_COMPILER_PREFIXenv.sh 探测结果comm.mk 的 G_COMPILER_NAME，拼出 CC/LD/AR/OBJDUMP/OBJCOPY/GDB
CROSS_COMPILER_PATHenv.sh 探测结果comm.mk 的 CROSS 前缀路径
OSZ_CROSS_ARCHenv.sh / 默认 rv32gcomm.mk 的 G_MARCH → module.mk 的 -march
OSZ_CROSS_ABIenv.sh / 默认 ilp32dcomm.mk 的 G_MABI → module.mk 的 -mabi
QEMU_PATHenv.sh / 默认 tools/qemuMakefile 的 QEMU，仅 run/debug 使用

三个“未设置时与旧版一致”的默认值：前缀 riscv32-unknown-elf、-march=rv32g、-mabi=ilp32d。所以只在官方工具链机器上开发的同事，行为零变化。

# 老路径（完全不动）
bash construct/build_make.sh all

# 换机器：两个变量，不改任何仓库文件
export OSZ_CROSS_ROOT=/opt/xpack-riscv-none-elf-gcc-15.2.0-1
export OSZ_CROSS_PREFIX=riscv-none-elf
bash construct/build_make.sh all

# 工具链放在仓库里（该目录已 git-ignore）
ln -s $HOME/tools/xpack-gcc tools/toolchain
bash construct/build_make.sh all

# 目标参数需要改（例如给只有软浮点的工具链）
export OSZ_CROSS_ARCH=rv32imac OSZ_CROSS_ABI=ilp32
bash construct/build_make.sh all

与旧版的四处行为差异

旧行为现行为原因
强制 ln -s ~/tools/toolchains tools/toolchain，再要求 tools/toolchain/<prefix>/bin不再创建链接；先按四个来源查找，找不到才回退旧路径解压写死目录结构，换机器必挂；且会覆盖用户已放好的 tools/toolchain
工具链不在位时报 Error: not fount …tar.gz报四个来源清单 + 两种修复方式原错误信息只指出“缺压缩包”，与真实原因（工具链在别处）无关
QEMU 目录/Tar 不在位直接 exit -1只告警，编译照常进行编译不需要 QEMU；把 run/debug 的前置条件当成全局前置条件会挡住纯构建
任何主机都解压仓库自带 qemu 包仅 Linux 主机解压；其他主机提示自行提供tools/qemu.tar.gz 是 Linux/x86_64 包，在 macOS 上解压只会得到不可执行文件
与 CMake 路径的唯一能力差异：Makefile 侧没有 C++ 语言，因此不存在 OSZ_REQUIRE_CXX 这类闸门；C++ 前端缺失对 Make 构建无影响。若某天有人往 Make 构建里塞 .cpp，需要另行处理。

08排错手册

现象根因处理
cannot execute 'cc1plus'工具链缺 C++ 前端，但 CXX 被强制启用本版已自动跳过 CXX；若被 OSZ_REQUIRE_CXX=TRUE 拦住则换完整工具链
链接阶段报 cannot find qc / libxxx.a工具注册用了共享的 find_program 缓存变量，ar 被误认成 gcc已修：每个工具独立变量 OSZ_TOOL_<tool>
arch_adapter.h: No such file or directorykernel/base/mem 未声明对 arch_riscv 的依赖（只在交叉构建暴露，宿主单测走 OSZ_TESTING 分支）已修：PRIVATE_DEPENDENCIES arch_riscv
tools/toolchain 指向不存在的 /home/xxx旧提交把符号链接纳入了版本控制本版已从 git 移除并忽略；本机重新指向自己的工具链即可
配置报“找不到 RISC-V 交叉工具链”四个来源都没命中按提示设置 OSZ_CROSS_ROOT/OSZ_CROSS_PREFIX，或把 <prefix>-gcc 放进 PATH
ELF 产出但地址不对链接脚本选择错误确认 -T construct/osz.ld，并用 readelf -h 核对 entry 与段地址
日志里 [TOOLCHAIN] 前缀 riscv32-unknown-elf，但 bin 目录里是 riscv-none-elf-gcc①find_program 缓存未清，变量已定义就跳过搜索；②toolchain 文件在 project() 之前执行，CMAKE_SOURCE_DIR 为空，tools/toolchain 一级查不到已修：每轮 unset 普通变量与 cache、改用 CMAKE_CURRENT_LIST_DIR 推仓库根，并新增编译器文件名一致性自检
换工具链后重新 configure，仍用旧编译器路径编译器路径固化在 CMakeCache.txt删除构建目录重新配置（rm -rf build）
Make 路径报 unterminated call to function `shell'（Makefile:13）make 把未转义的 # 当成注释起点，grep '^#' 被截断；GNU make 3.81（macOS 自带）直接报错已修：改用 awk -F= 'NF>1' 只取含 = 的行，语义等价
Make 路径编译成功但 run/debug 找不到 qemu本机无 tools/qemu/bin/qemu-system-riscv32，或自带包不是本机平台编译不受影响；需要运行验证时自行安装匹配平台的 QEMU，或设置 QEMU_PATH

cmake -S . -B build -DOSZ_CROSS_ROOT=<root> -DOSZ_CROSS_PREFIX=<prefix>
