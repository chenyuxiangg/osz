01背景与目标

OSZ 已经有一套可用的 host 侧 gtest（test/unit），但它刻意只覆盖与架构无关的纯 C 模块。凡是“必须真机才能验证”的部分——启动、调度、中断、异常、IPC、内存实况、驱动——目前依赖手工看串口，没有任何可判定、可回归的执行基线。

1.1现状证据

  • test/README.md 明确声明依赖中断 / 任务 / 堆 / 汇编启动的代码“暂不纳入测试范围”，覆盖仅 dlink / sortlink / strtoul。
  • targets/qemu_virt/src/main.c 里的 test_thread1_handle / test_thread2_handle 是人工观察的 demo，靠 printf 与人眼判断，无判据、无统计、无退出码。
  • kernel/dfx/src/task/dfx_task.c 只有一条 task 打印命令，属于“信息展示”，不构成断言。
  • kernel/base/trap/exception/src/exception.c 在异常后 while(1) 死等；一次野指针就会让整轮手工测试失去全部后续信息。
  • 构建侧只有 target_qemu 一个可执行目标，没有“测试镜像”概念，测试代码必然混入产品路径或被临时改 main.c 代替。

1.2设计目标

目标定义（可验收的口径）
可判定每个用例产出 PASS / FAIL / TIMEOUT / CRASH / SKIP 之一，宿主侧可据此算退出码，不依赖人眼。
可隔离单个用例的失败、异常、状态泄漏不影响同轮后续用例；异常可被捕获并归因到具体用例与 file:line。
可回归功能与性能都落成可存档的基线文件；同一后端重复运行结果确定（同指令数 / 同判定）。
可扩展新增用例、新增目标机、新增外设、新增指标类型，都不需要改框架核心代码，只加注册项与配置。
不侵入产品镜像 target_qemu 行为一行不变；测试能力全部由 OSZ_CFG_TEST 与独立目标隔离。

1.3非目标

  • 不做宿主机上的“模拟内核”以替代板上验证——那是 gtest 的职责边界，两者互补不重叠。
  • 不追求周期精确的性能数字。QEMU 与 wasm 平台都不是 cycle-accurate，本设计用确定性代理指标（退役指令数）承担回归判据，真实时间指标只在硬件可用时启用（见 §6）。
  • 不在 P0 引入任何第三方测试框架（Unity / ztest / CMock），也不引入 C++ 依赖。
  • 不做代码覆盖率插桩（裸机上无文件系统与 gcov 运行时）；以“接口触达清单”替代，见 §5.3。

02总体架构

四层结构，自上而下：宿主编排层负责起停、解析、判定与存档；执行面负责“怎么在目标机上把套件跑起来”；on-target harness 负责注册、断言、恢复与报告；被测对象只通过公共 API 与 observer 暴露给 harness。

2.1贯穿全框架的三条不变量

不变量含义怎么保证
产品镜像零影响未定义 OSZ_CFG_TEST 时，test/sys 不参与编译，exception_handler 行为与今天逐字节一致。所有改动 #if OSZ_CFG_TEST 包夹；target_qemu 依赖列表不新增任何测试模块。
用例只依赖公共 API用例不得直接读写 g_tasks[] 以外的内核内部状态；需要观测时走 observer 层。test/sys/harness/src/observer.* 集中封装 TASK_* 宏、hook 表、softtimer 表，重构内核时只改一处。
结果可重复同后端、同工具链、同编译选项下，同一套件两次运行的状态与指令数一致。注册顺序由链接顺序固定；用例禁止依赖未初始化的内存与真实墙钟；bench 用确定性代理。

03关键设计决策

下表是会影响长期演进的六个决策。每条都写明“不这么做的代价”，便于后续评审推翻时有据可依。

决策点选择理由代价 / 缓解
用例发现链接段注册 .osz_test与 .osz_cmd 同构（construct/osz.ld 已有 __cmd_start/__cmd_end 范式）；零 malloc、零初始化顺序依赖、顺序确定。新增链接段需同步 KEEP()，漏写会被 GC 掉；用链接后 nm 校验 __test_start/__test_end 非空。
镜像形态独立 target_qemu_test + 产品镜像内可选 test 命令autorun 需要“跑完即退出”，产品镜像需要“永不退出”；两者 main() 语义冲突，只能分镜像。模块依赖列表重复一次；抽 OSZ_KERNEL_MODULES 变量共用。
断言实现自研，4 个宏 + 1 段恢复汇编零第三方依赖（仓库纪律：仅 printf 一个外部依赖）；可直接复用 g_os_hook.print 与 printf，不用适配 stdio/malloc。功能比 Unity 少（无浮点断言、无参数化）；按需增量加，不做一次性对齐。
崩溃处理exception_handler 在测试构建下可恢复把“死等”变成“可归因的 CRASH 并继续”，是整套框架价值最高的能力；否则一次野指针毁掉整轮结果。需改产品文件；用 OSZ_CFG_TEST 包夹，并在 P1 加“产品镜像回归”用例反向确认未生效。
超时两级：用例内 bounded wait + 宿主全局超时内核已有 osz_delete_task（会回收 STACK_MEM_DYNAMIC 栈）与 osz_task_suspend/resume，但没有 IRQ detach 与句柄级回收；softtimer 回调跑在独立 swtmr 任务，跨任务 longjmp 会踩栈。卡死在纯用户态死循环的用例只能靠宿主超时判整轮失败；P2 用 mtime 中断改写被中断任务上下文再补硬超时。
性能指标确定性代理（退役指令数）承担回归判据QEMU 与 wasm 均非 cycle-accurate，墙钟时间随宿主负载抖动，无法做阈值判定；指令数与真实工作量单调相关且完全可重复。无法反映 cache / 分支预测；真机接入后启用 mtime 时间类指标，两套并存（§6）。
决策：为什么不把测试塞进现有 target_qemu 现有 target_qemu 的 main() 结尾是 first_schedule(); while(1);，这是 RTOS 的正常形态。若在其中插入测试入口，就必须用编译开关或 shell 命令区分“演示 / 测试”，两种语义会长期纠缠在同一个 main.c 里，且任何一次误配都会让产品镜像带上测试代码。独立目标把这段纠缠消灭在构建期。

04on-target harness 详细设计

harness 自身约 600 行 C。设计原则：所有容量上限来自 Kconfig 常量，不使用堆；所有状态机显式可枚举；对内核的依赖收敛到一个 observer 文件。

4.1用例元数据模型

元数据从第一版就按“未来要加外设、性能、压力测试”来定字段，避免后期改结构体引起全量重编。字段全部为编译期常量，落在 .osz_test 段，运行期只读。

字段类型语义用途示例
suiteconst char*模块域，取内核目录名sched / mem / uart
nameconst char*用例名，[a-z0-9_]priority_preempt
fnvoid(*)(void)用例体—
kindenumFUNC / PERF / SOAK / CONTRACT决定是否进默认套件、是否产出指标
tagsuint32 位图FAST/SLOW/IRQ/MEM/NONDET 等--tag fast 做提交前快速门禁
capsuint32 位图所需能力：UART/TIMER/PLIC/SPI/DMA板上缺该能力 → 自动 SKIP，不报失败
timeout_msuint32软超时（bounded wait 预算）0 表示取全局默认
costuint8预计耗时档位 1–5runner 用于排序、分片、soak 配比
versionuint16用例自身版本基线文件按用例版本绑定，避免改断言后误判回归
 
/* test/sys/harness/include/osz_test.h  —— 宏形态只暴露必要参数 */
typedef enum { TC_FUNC, TC_PERF, TC_SOAK, TC_CONTRACT } tc_kind_t;

typedef struct {
    const char *suite;
    const char *name;
    void      (*fn)(void);
    uint32_t    tags;        /* TC_TAG_* 位图 */
    uint32_t    caps;        /* CAP_* 位图   */
    uint16_t    timeout_ms;
    uint8_t     cost;
    uint8_t     kind;
    uint16_t    version;
} osz_test_case_t;

#define OSZ_TEST(suite_, name_, ...)                                  \
    static void t_##name_(void);                                      \
    static const osz_test_case_t tc_##name_                           \
        __attribute__((section(".osz_test"), used, aligned(4))) =     \
        { #suite_, #name_, t_##name_,                                 \
          .kind = TC_FUNC, .cost = 2, .version = 1, __VA_ARGS__ };    \
    static void t_##name_(void)

/* 用法 */
OSZ_TEST(sched, priority_preempt, .tags = TC_TAG_FAST, .cost = 1)
{
    ...
}

4.2注册与发现

沿用 .osz_cmd 的做法：链接脚本在 .data 末尾加一段 KEEP(*(.osz_test))，导出 __test_start / __test_end。runner 用指针步进遍历，天然按链接顺序排列（kernel 目录 add_subdirectory 顺序 + 文件名字母序 = 稳定顺序）。

/* construct/osz.ld —— 紧跟 __cmd_end 之后 */
. = ALIGN(0x20);
__cmd_start = .;
KEEP(*(.osz_cmd))
__cmd_end = .;
__test_start = .;          /* 新增 */
KEEP(*(.osz_test))         /* 新增：仅测试构建有内容 */
__test_end = .;
_data_end = .;
构建期自检（防止“0 个用例静默通过”） 链接后跑一次断言脚本：__test_end - __test_start > 0 且能整除 sizeof(osz_test_case_t)，否则构建失败。历史上最危险的失败模式不是用例挂掉，而是一个都没被链接进来却显示全绿。

4.3断言与恢复

断言分致命与非致命两级：非致命只记账并继续（用于一次跑出多个差异点）；致命立即终止当前用例并回到 runner。恢复靠一段约 20 行的 RISC-V 汇编保存 ra/sp/s0–s11——只保存 callee-saved 与栈指针即可满足从用例函数任何位置跳回。

宏语义行为报告字段
TC_ASSERT(cond)致命不成立 → 记 FAIL + longjmpfile, line, expr
TC_EXPECT(cond)非致命不成立 → 记 FAIL，继续执行file, line, expr
TC_ASSERT_EQ(a, b)致命数值不等 → 打印双方值（%#x）file, line, a, b
TC_SKIP(reason)—立即结束，状态 SKIPreason
TC_REQUIRE(cap)—板缺该能力 → SKIP，不误报失败cap 名

异常可恢复的边界

只有同步异常（instruction/load/store access fault、illegal instruction、misaligned）走 longjmp：它们在测试任务自身的上下文里同步产生，sp 仍是该任务栈，跨栈风险为零。异步中断不进入该路径，中断仍在原有 trap 流程里处理。恢复动作固定为三步：记录 mcause/mepc/mtval 与当前 tid → 标记用例 CRASH → longjmp 回 runner。

/* kernel/base/trap/exception/src/exception.c */
UINT32 exception_handler(UINT32 mcause, UINT32 mepc)
{
#if OSZ_CFG_TEST
    if (tc_active_case() != NULL) {          /* 测试任务正在跑用例 */
        tc_record_crash(mcause, mepc, CSR_READ(mtval));
        tc_longjmp_to_runner();              /* 不返回 */
    }
#endif
    /* 产品路径：保持原有行为不变 */
    printf("mcause: %#x, mepc: %#x\n", mcause, mepc);
    ...
}

4.5状态卫生：snapshot / sanitize

板上测试最难的不是写用例，而是用例之间互相污染。内核虽有 osz_delete_task/suspend/resume，但没有 IRQ detach 语义，也没有“谁占用了哪个中断/软定时器”的登记，因此框架用“进入前记账、结束后比对、尽力修复”的策略，把污染变成可见的报告字段，而不是让它静默影响后续结果。

受管对象检测处理
任务扫描 g_tasks[0..OSZ_CFG_TASK_LIMIT) 的 TSK_FLAG_FREE用例新增未退出任务 → 记 leak=task；runner 标记该 tid 为“已知残留”，后续用例前再次提示
栈读 TASK_STACK_INIT_MAGIC 水位线（0x5A5AA5A5 未被覆盖的最高地址）水位超过阈值 → 记 stack_high；PERF 用例产出 R 类指标
中断记录 IRQ 向量 handler 指针用例结束后恢复原 handler（tc_irq_release），未恢复则强制还原并报警
softtimer统计活跃定时器数量新增未删除的定时器 → 记 leak=timer，并尝试按登记表删除
内存堆已用字节数 / 空闲块数前后差值非零 → 记 leak=heap，附差值；配合 OSZ_CFG_MEM_DEBUG 可进一步定位块
 
[SZTEST] case_end mem.malloc_oom WARN ms=3 asserts=2 leak=heap(+16) stack_high=1520/2048
为什么“尽力修复”而不是“保证隔离” 只有 task delete、没有 IRQ detach 与句柄级回收的内核上，宣称强隔离是做不到的。与其做一套看起来严格、实际会漏的隔离，不如把残留如实上报：WARN 状态不失败套件，但会进入 result.json 的 warnings[]，长期跟踪它的趋势——如果某个用例持续污染，就是内核缺少 delete 接口的债，应该推动内核补齐，而不是在测试框架里伪造。

4.6报告协议

协议要求：人类可读、机器可解析、可在 4KB 一行的串口缓冲里完成、版本可演进。所有行以 [SZTEST] 开头，其余输出原样透传（与产品日志、shell 回显不冲突）。

[SZTEST] v1 suite_start total=42 board=qemu-virt caps=UART|TIMER
[SZTEST] case_begin sched.priority_preempt
[SZTEST] assert_fail sched_priority.c:88 "expect tid 2, got 3"
[SZTEST] case_end   sched.priority_preempt FAIL ms=12 asserts=4
[SZTEST] perf       sched.ctx_switch_rt min=1840ns med=2100ns p95=2600ns n=1000 instr=0
[SZTEST] case_end   irq.illegal_instr CRASH mcause=0x2 mepc=0x80001234
[SZTEST] case_end   uart.loopback SKIP cap=UART
[SZTEST] suite_end  pass=38 fail=2 crash=1 skip=1 ms=3120
行类型必需字段解析规则
suite_starttotal, board, caps建立会话；缺此行则整轮判 INCOMPLETE
case_beginidid = suite.name，与注册表一致；开始计时与超时监控
assert_failfile:line, msg可 0..N 条；计入 asserts 并附着到当前用例
perfmetric…, n自动转成 perf.json 条目，按 (backend, board, case, metric) 入基线桶
case_endid, status, ms状态取值 PASS/FAIL/TIMEOUT/CRASH/SKIP/WARN
suite_endpass/fail/crash/skip与 case_end 计数交叉校验；不一致即报协议错误

演进规则：新增行类型必须带版本号并保持旧行不变；解析器对未知行类型只记录不失败；v1 的字段一旦发布即冻结。这条规则让“三年后新增外设测试指标”不需要回头改解析逻辑。

05测试层次与用例矩阵

用例分层不按代码目录，而按“失效模式”分：功能正确性、时序与并发、资源与边界、故障与恢复、性能与容量。这样即使内核重构目录，用例矩阵仍稳定。

5.3接口触达清单（替代覆盖率）

裸机无法跑 gcov。改用一份可维护的清单：把内核公共 API 列进 test/sys/coverage_manifest.txt，harness 在链接期生成“被引用的 API 符号”，runner 比对清单输出“未触达接口”。它不衡量行覆盖，但能防止“新加了一个 API 谁都没测”这种更常见的债。

06性能测试设计

性能测试在这套框架里不是“跑一下看看快不快”，而是可存档、可比对、有阈值的回归资产。核心难点是：QEMU 与 wasm 都不是 cycle-accurate，因此不能拿墙钟当判据。

6.1三类指标

类别指标测量手段可信后端
T 时间类上下文切换延迟、IRQ→handler 时延、IPC 往返、malloc 单次耗时、softtimer 漂移CLINT_GET_MTIMER，分辨率 100 ns（TIMER_CYCLES_PER_US = 10）真机；QEMU 仅作量级检查
C 计数类退役指令数、trap 次数、调度次数、分配块数sim 平台 StepN 步进可数；QEMU 侧以 -icount 或指令计数器辅助sim（确定性最佳）；QEMU 参考
R 资源类峰值堆占用、栈最高水位、任务并发峰值、空闲时间占比内存记账 + TASK_STACK_INIT_MAGIC 水位 + 调度计数三后端一致

6.2确定性代理指标的必要性

判据选择 QEMU 的 TCG 把每条 guest 指令翻译成数十到数百条宿主指令，宿主负载一抖动，同一段代码的墙钟时间就能差两倍；wasm 平台同理。因此性能回归判据默认用 C 类（退役指令数）：同后端、同工具链、同编译选项下，指令数是确定性的单值，与真实工作量单调相关。T 类时间指标在 QEMU/sim 上只做“量级是否离谱”的粗检（例如上下文切换不该出现毫秒级），不作为通过/失败判据；真机接入后才启用阈值。

6.3测量协议与统计口径

  1. 预热：丢弃首轮（cache、分支预测、翻译缓存、惰性初始化都不稳）。
  2. 采样：默认 N=1000 次；cost≤2 的用例可 N=10000；单次套件总耗时上限由 runner 兜底。
  3. 统计：T 类报 min / median / p95 / max，并剔除首尾各 5% 采样；C 类报单值 + 上下界（应为 0 抖动）。
  4. 环境钉死：-O2 与 -Os 分别建桶；关闭不相关中断；单用例独占运行，不与其它用例交错。
  5. 分桶键：(backend, board, toolchain_commit, build_flags, case_version)。五元组任一变化即视为新基线，不做跨桶比较——这是避免“换工具链后全员误报回归”的关键。

6.4基线、阈值与判定

指标类型方向告警阈值失败阈值
C 类（指令数）越小越好+3%+10%，或绝对值 > 基线 +2000
T 类（真机时间）越小越好+15%（取 median）+30%，且连续两次运行复现
R 类（峰值堆 / 水位）越小越好绝对值超预算超出预算 20%
抖动量（p95/min 比值）越小越好> 3×基线> 6×基线（通常意味着新增了阻塞或锁竞争）

基线文件为 test/sys/baseline/<backend>/<board>/perf.json，人可读、可 diff、进版本库。更新基线必须走显式命令 run_systest.py --update-baseline --reason "…"，并把原因写进文件头，防止“一改基线就绿”。

6.5首批性能用例

用例度量为什么重要
perf.ctx_switch两次 resume 之间的 mtime 差；指令数RTOS 最核心的延迟预算，任何调度改动都会动它
perf.irq_latencymtimecmp 触发到 handler 第一条指令实时性承诺的硬指标
perf.ipc_roundtripevent write→read 完整环路IPC 改动最容易悄悄变慢
perf.malloc_churn1k 次 alloc/free 的指令数与最坏单次碎片算法（best-fit）改动的主要风险点
perf.softtimer_drift100 周期累计偏差时基与 tick 配置正确性
perf.sched_fairness同优先级 N 任务各获得的时间片分布防止调度器饿死某个任务

07外设测试的长期设计

外设测试将来一定会来（UART 之后是 PLIC、SPI/I2C、DMA），而且形态会变（回环、对端模拟、故障注入）。框架现在就要把三个位置留出来：能力描述、rig 抽象、中断所有权。

7.1device contract 七项检查

任何新外设驱动接入时，按同一张清单产出 CONTRACT 类用例。它不验证业务，只验证“驱动作为设备契约实现是否合格”——这类用例可复制性极强，是长期收益最高的部分。

#契约项可断言化检查点
1探测与标识复位后可读到预期 ID/版本寄存器；不支持的型号返回明确错误码
2寄存器语义可写字段回读一致；只读位写入无效；保留位保持 0
3复位默认值初始化前读到的默认值符合手册；初始化后关键寄存器达到预期值
4中断送达与清除触发条件成立 → handler 被调用恰好一次；清除后不重复进入
5数据面正确性发送/接收字节序列逐字节一致；边界长度（0/1/最大）行为明确
6错误路径超时、溢出、非法参数返回明确错误码且不破坏后续操作
7并发与重入中断上下文与任务上下文同时访问时无竞态（用原子计数或事件序列验证）

7.2rig 抽象：不侵入具体驱动

/* test/sys/rigs/rig.h —— rig 只依赖驱动对外暴露的接口 */
typedef struct {
    const char *name;
    uint32_t    caps;                 /* 需要的能力位 */
    uint32_t  (*open)(void *cfg);     /* 建连：回环 / 对端 / 注入 */
    uint32_t  (*inject)(const void *buf, uint32_t len);
    uint32_t  (*expect)(void *buf, uint32_t len, uint32_t timeout_ms);
    void     (*close)(void);
} tc_rig_t;
  • loopback rig：QEMU 可用 -serial 管道实现自环；真机用跳线。测数据面一致性。
  • fake peer rig：在驱动 HAL 层注入假的接收/发送实现（例如 SPI 从设备应答），不需要硬件对端。测协议时序。
  • fault rig：按调用序号注入错误返回值或不触发中断，专测错误路径与超时。这类 rig 复用 test/sys/harness/src/fake/ 下的桩。

关键约束：rig 只允许出现在 test/sys/rigs/ 并被 OSZ_CFG_TEST 守护，不得反向进入 kernel/drivers。驱动为了可测性需要暴露的接口（如发送完成的回调）应作为正式 API 提供，而不是测试专用的 #ifdef 后门。

7.3中断向量所有权

当前中断表是全局的，两个用例抢同一个向量会串味。引入轻量所有权机制：

tc_irq_hook_t *tc_irq_claim(uint32_t vec);   /* 记录原 handler，返回可安装新 handler 的槽 */
void           tc_irq_release(tc_irq_hook_t *h); /* 还原，幂等 */

bank 用固定数组（上限来自 Kconfig，默认 OSZ_CFG_TEST_IRQ_MAX = 8），不 malloc。sanitize 阶段对未 release 的槽强制还原并记 leak=irq。这条机制让“中断相关用例”从不可并置变成可并置，也是未来 PLIC 多源测试的前提。

7.4caps 与板级矩阵

每个目标机一份 targets/<board>/board.caps（纯文本，一行一个能力），构建期生成 board_caps.h；runner 直接读同一个文件。harness 与 runner 用同一份能力描述，避免“板上 SKIP 了但 runner 还期待它通过”。

能力qemu-virtwasm sim未来硬件板
UART有 ns16550有 控制台按板填
TIMER有 CLINT有按板填
IRQ_EXT有 PLIC部分按板填
SPI / I2C / DMA无 → 用例 SKIP无驱动就绪即填
RESET_HOOK有 进程级有 重装 ELF需继电器/调试器命令

7.5落地顺序

  1. UART：先做 fifo_echo（已有 shell_write_fifo 可注入）+ contract 七项，验证 rig 抽象成立。
  2. CLINT/TIMER：contract + perf.irq_latency，验证“中断所有权 + 性能度量”组合。
  3. PLIC 多源：验证多向量并置与优先级，此时 tc_irq_claim 的价值才真正兑现。
  4. SPI/I2C：fake peer rig，无需硬件。
  5. DMA：一致性用例（写后读、缓存伪共享），依赖真机或支持 DMA 的仿真板。

08宿主侧 runner

一个 Python 3 脚本（无第三方依赖，serial 后端按需可选 pyserial），三后端一套参数。设计目标是“任何人 clone 下来两条命令就能跑”，以及“CI 里能拿退出码和 JUnit”。

8.1三后端契约

后端起停方式结果判定特殊能力
qemu拉起 qemu-system-riscv32 -machine virt -nographic -kernel <elf>，串口走管道优先读 suite_end；可用 test-MMIO 退出码；超时即 kill失败即快速失败（可 --keep-alive 保留现场）
sim复用 tools/sim/run_on_platform.mjs 的 wasm 内核，注入 ELF 并 StepN读 console 字节解析；指令总数取 stderr 统计指令数精确 → C 类指标基准后端
serial打开串口 → 执行配置的复位命令 → 读流同 qemu；无退出码则靠哨兵复位命令必须可配置，不写死任何板卡流程

8.2命令行与产物

11风险与对策

风险影响对策
用例残留任务/中断未释放高用例约定“自退出 + 不建常驻任务”；sanitize 上报 leak=task；长期推动内核补 IRQ detach 与句柄回收接口（delete 已具备），而不是在框架里造隔离假象
异常恢复改变产品行为高全部 #if OSZ_CFG_TEST；P1 增加一条“产品镜像 exception 路径未改变”的反向检查（对比反汇编 exception_handler 符号）
用例为 0 却全绿高链接期校验 __test_end > __test_start；runner 要求 suite_start.total > 0 且与 case 计数一致
用例与内核内部耦合中只允许通过 observer.c 访问内部宏；评审时把直接访问 g_tasks[] 视为缺陷
QEMU 性能数字被误当真实数据中报告里 T 类指标在 qemu/sim 后端标 indicative-only，不参与判定；判据固定走 C 类
链接段被 GC 掉 / 优化掉中used + KEEP()；构建后 nm 校验 __test_start 存在
测试镜像与产品镜像依赖漂移低共用 OSZ_KERNEL_MODULES 变量；CI 后续比对两目标的链接符号集差异
协议变更破坏历史解析低v1 字段冻结；新增行走版本号；解析器对未知行宽容

实现期发现的两个真实缺陷 ① 启动栈与堆重叠：start.S/trap_entry.S 的 .section .stack 未标 @nobits，链接器把 __system_heap_start 排到了启动栈首地址，内存池初始化直接踩掉启动栈，测试镜像上电即 trap。已改为 "aw", @nobits，堆起点落到栈之后（0x84006920）。 ② 仿真后端不传递异常：一旦取异常就 halted reason=Trap，所以 CRASH 路径（异常可恢复）在 sim 上无法验证，只能等功能用例；mtime 的 64 位读在 sim 上偶发返回异常值（一次读数跳到 2051 秒），harness 已加单调钳位防御，平台侧待查。
